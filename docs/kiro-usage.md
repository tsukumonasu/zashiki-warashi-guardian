2026-11-21 | spec `voice-conversation` | Full spec (requirements, design, tasks) and the implementation of a spoken conversation with family members (Amazon Nova Sonic through an AppSync Events API, one `voice-session` Lambda per conversation, an audio client on the doll and one in the browser), executed task by task from `tasks.md` with sub-agents (one task per run, a checkpoint task after each group, property-based tests as required tasks). **Design review:** Kiro reviewed the draft design against the AWS documentation and the repository rules and recorded 19 findings (V1 to V19) in `design.md`, each with the original assumption, the evidence and the decision. Examples: the doll cannot call Bedrock itself, because the bidirectional stream needs an HTTP/2 transport that is not available for armv6l and the doll holds no AWS credentials (V4), so a Lambda owns the stream; the doll authenticates with a per-session token checked by a Lambda authorizer instead of SigV4 (V5); `audioop` is gone in Python 3.13, so the microphone gain is a small pure function (V8); AppSync Events documents no ordering guarantee, so every audio frame carries `seq` and the receiver reorders in a small window (V9); a crashed Lambda never releases its lock, so the lock stores `expiresAt` and a later start takes it over (V11); the model can emit any tool arguments, so `toolToCommand` is pure and total and clamps to the head limits in `hardware.md` (V14); reviewer voice is off by default (V15). **AWS checks through the `aws-docs` MCP server** (cited in the "Verified AWS facts" table of `design.md`): (1) Japanese is not officially supported by Nova 2.5 Sonic. The language list and the service card name English, Spanish, German, French, Italian, Portuguese and Hindi only and warn of reduced accuracy for other languages, while the owner's own listening tests say the polyglot voices work. Kiro therefore wrote Japanese as a risk instead of a fact (V1): a prompt that demands Japanese, a pure language check on the first assistant turns, cached voice lines when it fails, and a kill switch, with quality marked "pending owner measurement". (2) The IAM action for `InvokeModelWithBidirectionalStream` is `bedrock:InvokeModel`. The Service Authorization Reference lists no action of its own for it, so the `voice-session` role gets `bedrock:InvokeModel` on the one foundation-model ARN. (3) The minimum value of the Lambda asynchronous maximum event age is 60 seconds. The first draft wrote 30 seconds for `voice-session` and `voice-grant`; the CDK code and the template tests use 60 (`cloud/lib/voice-stack.ts`, `cloud/test/voice/voice-stack.test.ts`). (4) Model ids and lifecycle (`amazon.nova-2-5-sonic`, In-Region in Tokyo only, no Geo or Global profile, 8-minute connection limit, 20 concurrent sessions by default), AppSync Events quotas (25 publishes per second per connection, 240 KB per subscription message) and the Lambda authorizer behaviour. **Property-based tests:** Hypothesis (device) and fast-check (cloud, dashboard) cover the session lifecycle reducer (every path ends in one terminal phase and cleanup runs once), the one-session-per-doll lock including takeover after `expiresAt`, the tool limits (every tool input maps to a command inside the configured limits or to an error, and every `toolUse` gets exactly one `toolResult`), the frame and message schema round trip against golden fixtures read by Python, TypeScript and the dashboard (`docs/fixtures/voice-v1/`), the microphone gain with clipping, the reorder window, and the pure cores of the state machine and the language check. **Fake-first approach:** every dependency sits behind a small adapter with a fake, so `make test` needs no Pi, microphone or AWS account. The Bedrock stream is replayed from scripted event streams of recorded-style audio (`sonic-session-ok.jsonl`, `sonic-session-tools.jsonl`: short synthetic audio and placeholder text, no real voice), and the AppSync, DynamoDB and MQTT sides have in-memory fakes. Real-service checks exist only as opt-in tests and scripts. **Persona marker decision:** the system prompt must not drift from `persona.md`, so a list of marker phrases, one per persona rule, is kept in `docs/fixtures/voice-v1/persona-markers.json`, and a drift test checks that the prompt contains each phrase and that sample output contains no blocked word. The prompt wording stays in code; the markers are the check. **Still unverified:** Japanese quality, AppSync Events frame ordering, end-to-end latency, how early the assistant text arrives before the audio (V13), the price of one session (V19) and echo on the real doll. No deployment, real Bedrock call or microphone run was done by Kiro. **Left to the owner:** opt in with `voiceEnabled = true` and deploy `VoiceStack` (O1); confirm Bedrock model access and AppSync Events in `ap-northeast-1` (O2); run `scripts/check_sonic_japanese.py`, `scripts/check_appsync_ordering.py` and the opt-in integration tests, then record value, date and source in `design.md` (O3); decide the open questions (reviewer voice, stranger during a conversation, cascaded fallback, voice and model); install `python3-websockets` on the doll and set `conversation_enabled = true` only after the measurements pass (O8) | Chose the default model and voice, kept reviewer voice off, decided that Japanese stays a measured risk with the fallback ladder until the owner records a pass, and kept the owner steps out of the automated tasks | `.kiro/specs/voice-conversation/{requirements,design,tasks}.md`, `docs/fixtures/voice-v1/`, `cloud/lib/voice-stack.ts`, `cloud/test/voice/voice-stack.test.ts`
